# 执行层架构复核（2026-09-07）

本次复核基于 0.3.58 源码、只读事件账本和本机 DSH 实现。执行层修复保持 `dsh_native_plugin_evolution@1` 的真实 Agent 调用契约：未增加生产 Host 绕过，未改历史数据或已交付包。

## 已修复的生命周期问题

1. **满载队列的取消延迟。** Provider 达到并发上限时，已排队请求原先必须等其他任务释放容量，才会被扫描并取消。现为每个请求监听取消，在排队状态立即移除队列、清理定时器并结束等待；已经开始的任务保留物理占用，直到实际执行和清理结束。
2. **等待结束后的定时器残留。** 原先每次启动间隔等待会新建一个完整阶段 deadline timer，提前完成时没有清除。现复用原有排队 deadline 及同一个 AbortSignal，不再留下多余长寿命计时器。
3. **取消后的观测一致性。** 已启动请求收到取消后归为 `draining`，不会继续显示为正常活动请求；Provider 的实际占用计数仍包含清理中的请求。

实现位于 `integrations/dsh_ecology_plugin/lib/runtime/provider-stage-gate.js`，新增回归测试为 `integrations/dsh_ecology_plugin/test/provider_queue_lifecycle.test.mjs`。测试先确认旧实现的四项失败，再验证修复。联合队列、stage runner、取消竞争、launch fence 共 110 项 Node 测试通过；其中新测试 5 项。

## 并发与成本边界

| 层级 | 当前规则 | 含义 |
| --- | --- | --- |
| 原点工作线程 | `min(pending_origin_count, sample_concurrency)` | 不按候选数预先除小线程数 |
| 单运行准入 | 冻结的 sample concurrency，共享自适应窗口 | 多候选共同使用一个窗口 |
| Provider 准入 | 默认最大 128，在运行间共享 | 不随候选、运行数量乘大 |
| Provider 启动间隔 | 默认 3,000 ms | 单 Provider 约每分钟最多启动 20 个新子会话，部署可覆盖 |
| 正式评测候选通道 | 最多 2 条，局部编辑短边界互斥 | 两条正式原点链可同时计算，编辑仍遵循修订身份 |

单原点包含同一时刻的 3 个变量 × 3 个时距。原生 Planner 只能选择一个冻结的向量预测工具；工具输入为 `tool_id`、`wave_digest`，数值预测由冻结的 Host 模型生成。正常 Planner 要经过 Skill、预测工具、结构化输出，通常涉及三次模型响应。因而“64 并发”是同时占用的上限，不意味着瞬间发出 64 个原点或每分钟完成 64 个原点。

本机 DSH 的 `agent`、`subagent`、`session` 实现未发现固定为 4 或 8 的样本准入上限。`session-persistence` 的 prepared-session capacity 是冷读准备结果的 LRU 容量，不能用它解释模型并发。

真实网页运行 `run:95dd094a-22ca-4908-a22e-a29058b78b83` 的初始观察：搜索计划从 01:54:41.446Z 到 01:55:01.539Z 返回；检索在 01:55:04.532Z 完成；研究综合随后开始，01:57:50Z 暂停前没有进入样本预测。此窗口只能说明前置研究阶段耗时，不能据此测算样本吞吐或认为样本线程发生串行化。

## 独立版本的执行研究方案

建议使用独立研究标识 `ecologyrsi-dsh.sealed-native-host-shadow/1`，先比较已完成、已观测的一个候选及固定原点集合。它只产生研究报告，不产生候选晋级事件，不参与原运行评分，也不修改生产原生执行协议。

对照应输出：输入、拟合状态、原生工具回执摘要；预测向量是否相等及最大误差；有效掩码、基线、评分是否一致；Host 纯数值耗时；同一原生会话集合的模型使用量、真实耗时、重试次数。模型报告的 token 应区分缓存、非缓存输入和输出，缺失用量不得计为零。

0.3.58 的 training-fit 诊断对照是 Host 内部平铺调用与按原点调用，所用拟合折也不同于真实运行。它能检验数值一致性，不能当成真实 LLM 对照或节省比例。上述独立 native/Host 对照尚需按这些输入条件执行，不能仅凭固定路由的代码结构宣称已经完成实测。

## 0.3.59 创建前模型预检的持久审计

要求模型契约预检的新运行在静态任务元数据中冻结 `model_contract_preflight_audit_schema=ecologyrsi-dsh.model-contract-preflight-recorded/1`。实际回执不进入任务元数据，避免刷新回执或改变时间戳后生成不同的任务摘要。

创建流程在 `RunCreated` 后、`RunStarted` 前写入唯一的 `ModelContractPreflightRecorded` 事件，绑定 run ID、任务摘要、两角色的模型/路由/预设/工具表面身份、回执摘要、通过时间和有效期。回执只保留工具顺序、结构化输出摘要及受限用量等审计字段，不归档原始提示、自由文本诊断或额外响应内容。

Director 和事件重放都会阻止要求新审计的运行在缺少证据时启动。回执有效性按事件记录时刻验证；历史记录不会因为当前时间超过 TTL 被撤销或要求重新调用模型。历史任务没有新静态标识时沿用原启动契约，界面不会据旧布尔要求伪造已通过状态。

完整详情、运行列表、监控和控制响应使用一致的 `model_contract_preflight` 对象：`status`、`scope`、`checked_at`、`roles`、`audit_digest`、`audit_required`。`verified` 明确指 `tool_and_schema_transport_only`；它不涵盖预测质量、研究结论、科学认证，亦不证明所有 Provider 计费项均已完整返回。

已持久化的创建命令按原始 HTTP 请求和所属资源恢复，不会因为 DSH 的动态 live capability 从 false 变成 true 而重新生成任务、误报幂等键冲突。已完成创建的幂等响应不依赖模型当前在线或外部预检回执仍然新鲜。如果中断发生在 RunCreated 已写入、seed 尚未物化的间隙，只有确认原任务摘要匹配后才绑定资源，并复用原 RunCreated 中冻结的 seed 恢复边界。这个持久运行保留原生角色宿主，不会被误当作从未创建的资源终止。创建中断后，未记录审计时读取匹配的有效回执；已记录审计时直接使用历史证据。显式 start 恢复也先完成 seed 和审计，再用更新后的 Host 事件修订激活原生运行。

新增 `tests/test_model_preflight_audit.py` 覆盖创建次序、安全投影、三类视图一致、两种审计中断恢复、显式 start 恢复、幂等时运行时离线、缺失审计拒绝、历史 TTL、身份/摘要篡改、重复事件和旧协议行为。

| 2 | `88d79445-bb87-45cd-bde9-87051456fdad` | 2026-09-07 02:32:05.230 | 8,192 | `max-tokens` |

第一次曾出现已由 DSH 内部重试的 `TRANSPORT` 错误，公开摘要为 `terminated`；最终失败原因仍是输出预算耗尽。两次最后响应只有 reasoning 类型、没有结构化工具提交。8192 是每次模型响应的输出上限，不能当成整个阶段的总 token 成本；输入、缓存、Skill 调用和内部重试仍单独产生用量。

原先 `runStructuredRole` 只在 `error` 或 `completed` 时读取会话终态分类，直接返回的 `max-tokens` 落入通用可重试模型错误。因此同一请求在同样的 8192 预算下再次执行。现优先使用原生终态，返回 `structured_child_output_budget_exhausted`，清理子会话且不再重复完全相同的调用。结构化执行和 stage runner 共 66 项回归通过；包含真实终态的缩减结构 fixture、滞后会话投影和单次启动断言。历史失败账本保持原样。

本轮可执行的对照是新建运行，明确冻结另一策略模型身份并重新预检，保留相同的数值预测协议和工具约束。旧运行不得原地改模型；新运行结果也只能证明新身份下的行为。

后续若单独研究 Kimi 的阶段成本，优先在独立执行协议中显式冻结 research-synthesis 的推理设置。本机 DSH 子会话支持 `agentOptions`，DeepSeek adapter 能将 `reasoningEffort=off` 转为 `thinking.type=disabled`，也接受 `low/high/max`；但这不能证明当前 pjlab/Kimi 远端接受或兑现这些设置。需要同模型、同冻结研究上下文的独立工具/结构化探针后才能启用，不能改 Provider 全局配置或静默套用。

另一项独立研究是压缩研究上下文中重复的完整 genome、计划与证据描述，同时保留全部目标/时距、原始证据身份、变异目录和预测器语义；以请求摘要和源上下文摘要绑定。原 schema 的 summary 上限 12,000 字符、最多 64 条证据、每方向多个长文本字段，远高于实际四方向报告所需。输出字段长度只约束最终报告，不能保证减少模型内部推理，因此不能将提示压缩单独宣称为已经解决本次预算耗尽。

实际 GLM 请求为 36,207 字符，其中 context 34,447、13 张证据卡 14,560、跨代经验 5,174、研究契约 4,936、完整 parent genome 3,636、搜索计划 2,983；结构化工具 schema 6,722 字符。安全诊断只统计输入结构及输出类型/长度，不归档推理正文。

本轮新增 `ecologyrsi-dsh.research-execution-policy/1`，仅新运行冻结 compact@1 上下文、concise@1 报告及 research-synthesis 显式 16,384 输出上限。其他结构化阶段仍受原 8,192 接口上界限制，并沿用各自更小的实际请求预算；本次 `sample.plan` 实际为4,096，canary 继续使用独立小预算。Python、stage runner、one-shot 三层核对新综合预算与阶段策略完全一致；策略处于 canonical context 内，因此 child item digest 和阶段 phenotype identity 同时覆盖预算。没有改变 Provider、模型或 reasoning effort，也没有放宽 Skill/结构化工具链。

短报告保留原 schema 和全部字段，summary 不超过 1,200 字符，最多 8 条证据，每方向的 hypothesis 不超过 400 字符，其他文字字段进一步收紧，引用最多 4 个原始标识。DSH 子任务启动校验器严格拒绝数值长度约束，因此最终模型 schema 只能保留文字描述；实际长度限制由 Host 返回验证执行。

## 真实启动校验与最终 schema 接缝修复

运行 `run:121a3305-e5fa-461c-ab0c-7db6a4e9ed09` 在搜索后、研究综合子任务创建前连续返回 `structured_child_start_failed`，没有对应模型会话或用量。根因是本轮短报告改动在第一次 DSH 兼容投影后重新添加了 `maxLength/maxItems/minItems`；DSH 的 `assertObjectJsonSchema` 对这些字段抛出 `UNSUPPORTED_SCHEMA`，并非 16,384 token 超过子任务上限。之前 stub 测试没有调用原生 schema 校验器，因而遗漏了这个接缝。

现以 `prepareStageOutputSchema` 统一执行阶段特化和最终 DSH 子集投影，确保任何阶段特化都不会把 Host 专用约束直接传到子任务；只有一个合法变异轴时直接使用其对象 schema，避免不合法的单成员 `oneOf`。短报告文字描述与 Python 严格验证保持不变。原生启动时若仍遇到 `UNSUPPORTED_SCHEMA`，明确归类为 `structured_child_output_schema_invalid`，即便包装为 HTTP 503 也不进入原生或 Host 外层同请求重试。

新增 `native_stage_schema.test.mjs` 直接加载安装的 DSH 原生校验器，覆盖全部 10 个实际阶段、紧凑研究的 1/4/8 方向与单/多变异轴，以及原生拒绝时的安全错误分类。本机这项验证没有跳过、没有模型调用。相关 Node 联合回归 79 项通过，Python 阶段预算及紧凑研究回归 8 项通过。未修改运行已冻结的搜索证据或历史失败事件。

HTTP 层也必须保留这个确定性分类。`routes.js` 的公开阶段错误白名单已加入 `structured_child_output_schema_invalid`，返回 HTTP 422 和这个受限错误码；未知异常继续返回脱敏的 HTTP 502 / `dsh_native_runtime_unavailable`。新增真实本地 HTTP POST 回归验证两条路径，确认原始异常中的私密字段不会泄露。HTTP 安全与原生 schema 校验联合回归 9 项通过，阶段预算 Python 回归 3 项通过，均不调用远程模型。

## 当前吞吐边界与后续调度协议范围

本轮原生验证最初采用3秒启动间隔；后续出现限流时使用共享退避，具体修复与证据见后文。恢复后的运行 `run:121a3305-e5fa-461c-ab0c-7db6a4e9ed09` 早期观察为 24 个成功原点、0 个失败、约 20 个在飞，完成速率约 16 origins/min；按这一短窗口外推 1,195 个 candidate-origins 约需 75 分钟。它是阶段性估计，不包含后续晋级、批次边界、独立评审和可能的退避，不能当成最终耗时或原生/Host 对比结果。

现成配置名为插件级 `structuredStageMinIntervalMs`，在 `resolvePluginConfig` 中默认 3,000 ms；没有同名环境变量覆盖，也没有现成的每运行冻结配置。`RuntimeController` 创建一个共享 `NativeStageRunner` / Provider gate，以模型 ID 的 Provider 前缀分组，因此同一 `pjlab` 的 GLM 与 Kimi、不同运行的阶段均共享同一启动时钟与物理并发上限。修改这个配置会影响该插件内的所有相同 Provider 运行，不能描述为仅调整某一运行。

3 秒最多启动约 20 个新子会话每分钟，常规样本的三个模型响应约对应 60 次模型请求每分钟；2 秒则分别约为 30 和 90。子会话内部工具续轮、DSH 内部重试、独立 canary 及其他应用的调用还会消耗 Provider 配额，因此启动间隔不是严格的账户 RPM 计量器。初始下限仍为3秒，实际间隔可因限流反馈扩大；没有提高配置的启动速率来绕过供应商配额。

已存在的 429 处理从原生终态提取有界 `providerRetryAfterMs` 或 `retry_after`，延长整个 Provider 的下一次准入时间；RPM 信号不会误降物理并发窗口，其他模型故障仍使用自适应减载。这个惩罚发生在 Host 观察到终态时，不能声称控制了 DSH 内部每一次模型请求，也不能假定成功终态前已恢复的内部 429 一定被这个 gate 观察并退避。

后续若开展吞吐优化，应为**新运行**增加单独的、带版本的静态 scheduler policy，冻结请求的 Provider 启动间隔、物理并发上限、退避策略版本及其摘要，并在原生启动绑定、子阶段准入和恢复校验中使用同一策略。旧运行保持原冻结语义。实现仍只保留一个跨运行 Provider gate，实际间隔不得低于部署允许的 Provider 下限，也不得消除已有 Retry-After 债务；同一 Provider 存在不同运行策略时采用保守的共享上限，不能按 run 新建多个 gate 倍增配额。投影需要区分冻结请求值、实际生效值与当前退避剩余时间。

是否把新运行的间隔从 3,000 ms 小步降到 2,500 ms 或 2,000 ms，必须先有对应账户的可用 RPM 与其他并发流量证据，再在明确的原点数、总时长和 token 上限内验证完成率、真实模型请求率、429、排队时间与 p95 耗时。研究用 Host 数值 shadow 只检验数值等价与 Host 耗时，不能代替这项真实 LLM 吞吐实验。本轮不实施这个新协议，交付验证以当前 1,195 原点的完整原生链为准。

## 真实运行中的宿主 CPU 热点与修复

电脑唤醒后继续同一运行，观察到55个原生样本已经返回，而宿主新增结算明显落后；后端持续约96–100% CPU，原生进程接近空闲。系统采样指向多个线程中的 `sorted`／JSON对象递归构造。只读剖析确认 `record_session_usage` 每次读取所有预留、已接受结果和累计用量事件；当其他线程更新运行修订时，CAS失败后又读取全部历史。一次剖析解码4018条事件，约0.252秒，主要耗在JSON不可变对象构造。这是宿主入账压力，不是模型科学评分变慢。

修复使用三个局部表达式索引，分别按run＋预留ID和run＋会话ID查询，并取唯一有序并集。必须保留两个身份轴：只查预留ID会遗漏会话已经归属于另一预留的冲突。读取不截断，不丢失早期累计用量约束，原有全运行CAS仍防止查询与提交之间的并发冲突。对应会话查询只解码7条记录；该次非剖析查询约0.000339秒，不能与启用剖析的旧查询直接计算加速比例。

完整重放原先对每条用量再遍历整个既有事件前缀。现在只索引已经通过验证的历史记录，按预留／会话找到完整相关前缀，避免未来事件影响早期回执。对同一8583条封存事件，用旧完整扫描校验函数与新索引函数分别回放，公开RunState逐字段相等；同环境非剖析耗时2.926秒和0.090秒。这个结果仅衡量宿主回放，不能表述成LLM执行加速或收费减少。

同时发现真实检查点遗漏了 `EvaluationScope`、`PlannedBatch/Cohort/Origin`、`KnowledgeCard` 及三个嵌套枚举。补齐显式白名单后，真实正式轨迹检查点可保存、冷恢复并与完整回放相等；未知模块名仍不能触发导入或执行。检查点仍是可丢弃派生缓存，事件账本继续作为权威来源。

## 共同留出阶段的供应商速率反馈

06:25–06:26Z，同一运行出现集中原生模型错误。只读核对两条会话的错误终态，供应商明确返回 `RATE_LIMIT / user_rpm_rate_limit_exceeded`，附13秒和3秒重试时间。系统原有共享门控会等待该窗口，但之后回到原来的3秒启动节奏，因此可能反复撞限。并发上限与每分钟发送速率是两个不同的约束，仅等待或减少候选数不能修复这个反馈缺口。

运行经网页暂停、排空后，修复供应商级反馈：RPM信号使该供应商的有效启动间隔翻倍，默认从3秒到6秒，最高60秒；至少相隔一个60秒或更长的惩罚窗口才再次增长。一个错误突发不会被多个候选重复放大降速；同一供应商的候选、运行和重试共享间隔，其他供应商不受影响。物理并发限制保持独立。有效间隔在进程存活期间保持，重启后重新学习；它控制子会话启动，不能宣称精确限制DSH内部全部模型请求。

离线回归验证20条同窗限流只触发一次降速、跨运行共享准入、供应商隔离、后续窗口再退避以及排队取消。随后安装对应原生包，重启服务并通过网页恢复原运行。此前12,216条事件、截止seq22419、809条已结算原点批记录的完整前缀摘要保持不变。既有失败继续保留，科学样本、模型、评分和冻结预算没有修改。


随后实际终态证据还区分出第二种429：`cluster_concurrency_rate_limit_exceeded`，供应商明确标记 `limit_type=concurrency`。它不能继续按RPM降速处理。最终分类器把明确的并发拥塞交给已有物理窗口减载，把RPM信号交给共享发送间隔；两种情况都保留有界等待与重试。93项执行层联合回归通过。此前同一阶段还记录了3次10分钟执行期限到期，这些失败和重试保留，不能据此宣称供应商可用性已有保证。

最终决策关口与限流维度修复一起在原运行暂停排空后加载。截止seq24944的14,741条事件与941条已结算原点批记录前缀核对不变；网页恢复返回HTTP200。此前完整源码检查为1586项Python与213项Node通过，最终交付仍需针对最后源码再次形成完整验证绑定。


原基准留出阶段还观察到原生Node进程约99–115% CPU，宿主Python约0.2%；1秒系统采样主要落在文件I/O完成回调后的JSON序列化，物理内存约796MB、历史峰值1.3GB。采样不足以定位某一DSH函数或证明内存泄漏，因此没有据此改写外部运行时。它说明仅修宿主索引、调整限流不能消除逐原点会话的持久化和序列化开销。运行仍在有界重试后推进；后续批次数值协议应减少这类会话数量，并分别测量原生和宿主成本。
