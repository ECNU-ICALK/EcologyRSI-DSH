分析日期：2026-09-09。对象：`run:9188de6e-0361-4e62-8857-bd013c2529c9`，主网页 8848 对应账本，证据截止 seq 71936。本次仅做只读审计并新增分析文档和统计文件，没有修改应用代码、模型配置、运行状态，也没有重启服务或调用远端模型。

**2. 直接根因与系统性放大机制**

**2.1 DSK Flash 把工具调用标记当成普通文本返回。**

致命请求为 sample.critic，session `f6eb2655-a398-4896-9493-1b36e52bf42e`。日志显示模型仅输出 46 tokens，以普通 assistant 文本返回 DSML 的 skill(origin-vector-review) 调用标记；没有真实 tool/call 事件，结束原因却是 completed/stop。

这不是输出额度耗尽或等待超时。seq 71909 在 12:42:02.101 记录协议错误，seq 71910 在 12:42:02.429 写出 RunFailed。随后 13 个 aborted 是取消其他在途任务的收尾。上一运行 872bf… 的 session `7f901180-b7f2-4d25-99b4-0d4927ded083` 具有相同形态。

现有证据只能定位到“进入 DSH 消息时已是普通文本”；尚不能区分是原始模型服务、网关兼容层还是 DSH provider 适配遗漏。下一步应在这些边界保留脱敏的响应形状与真实工具事件，定位 DSML 在哪里失去结构。工具授权必须继续依赖真实工具调用及宿主凭证。

**2.2 GLM 的 HTTP 503 在跨层传播时变成了 HTTP 422。**

对本运行全部 122 个 structured_child_model_error，按 reservation 关联 session，并逐个解压完整 Zstd 日志。122 个日志均可读取，结果为：121 个最终 SERVER/503，1 个最终 RATE_LIMIT/429。失败会话内部还记录了 618 次 SERVER 重试和 8 次 TRANSPORT 重试。它们是持续服务故障，不能解释成 122 次模型预测能力差。

目前的传播路径是：

`服务返回 503 → DSH 内部重试耗尽 → 被归为 model_terminal → 与可恢复模型错误共用一个 error_code → HTTP 层统一返回 422 → Python 判断不可重试 → 样本 remote_rejected → 失败罚分 → 后续 batch/评测继续`

具体问题有三处：

- DSH capture 分类主要识别 429/RATE_LIMIT；SERVER/503 落入 non-missing/model_terminal，错过共享服务降载。
- model 和 model_terminal 压成同一个 structured_child_model_error；HTTP 422 又抹掉上游状态和可恢复性。
- 样本适配器把异常转为正常返回的失败结果后，准入控制的成功分支可能把它视为健康完成，继续累积增并发条件。这一点是源码推导，账本缺少完整的自适应并发历史，不能声称已实测发生加并发。

**2.3 “尝试完”被当成可以推进科学流程的“完成”。**

正式批次和轮末评测的部分调度判断只要求 attempted 达到冻结样本数，因此 0/10、0/50 也能封存并进入下一阶段。后续完整性门槛确实禁止错误晋升，但此时额外成本已经消耗。

必须把三个结果分开：

| 类型 | 处理方向 |
|---|---|
| 服务、连接、协议或执行预算导致无法形成有效预测 | 运行恢复、路由冷却、证据不足或终止；科学效果不可评估 |
| 有效 Agent 预测，但效果不达基线或约束不合格 | 可按预声明规则保留冠军、修订或淘汰 |
| 有效预测且共同评测证据达到门槛 | 才允许探索性择优或正式晋升 |

失败惩罚可作为系统可用性/运行成本指标保留。是否把部署失败纳入复合业务评分，应单独声明；不能把它混成纯预测质量，并据此指导模型反思。 候选策略导致的冗长输出或工具预算耗尽，可以作为策略可执行性问题推动精简，但不能借无预测时的惩罚值证明预测误差改善。

**3. 这轮为什么没有产生可信进化**

- 四个预筛结果全部 passed=false。系统明确标记 exploration_only，并未暗中认定其合格；但仍完整消耗 Top 2 训练和轮末复评。
- 18 次局部编辑决策中，**16 次是因执行不完整自动保留旧版**，只有 2 次真正调用编辑 Agent。
- 两个修改分别调整 CO₂ residual scale 和 ridge_alpha。第一个比较虽然记录了正向分差，但冠军只有 9/10 有效样本，不能作为完整配对改进；第二个比较两臂都没有有效预测。
- 两条 FormalTrajectoryCompleted 的最终版本均为 **r0**，轮末评测也绑定 r0。没有得到本轮可信提升。
- 第一个方案的轮末副本 0 覆盖率为 0、score=-1，副本 1 覆盖率为 88%。第二副本不是对第一副本的恢复，不能填补首副本缺失的证据。

任意一个失败样本就禁止当前严格比较，是完整性保护；需要解决的是补全和停止机制。举例，在独立近似下，即使单次执行成功率为 98%，20 次配对执行全部成功的概率也只有约 67%。持续相关服务故障比这一近似更严重。增加轮数无法补偿执行基础不可靠。

对本轮冻结数据的检查，未发现需要放松时间隔离的证据：adaptation 最后标签时间早于 screening 起点，screening 最后标签时间早于 holdout 起点；下一训练批次也在上一批全部目标成熟之后。50 个轮末时点覆盖 8 天，重复推理副本没有被冒充成额外独立观测。应继续保留这些约束和逐样本 Agent 来源核验。

**4. 成本与展示还有哪些实际问题**

当前 100 指每个入围方案的正式训练时点数。最大正常预算仍为 `4×64 + 2×(10+9×20) + 3×50×2 = 936` 次样本执行/轮；5 轮最多 4680 次，不包括所有额外 Agent 工作与修复。此轮实际没有产生大量挑战版本，正式执行为 220，不能把 936 当成已经花掉的次数。

本次预测工具调用 2337 次；成功 planner 会话平均累计输出约 10610 tokens。按各 session 最新 provider 回执求和，上报总用量为 **41,595,620 tokens**，其中输出 5,910,744；这是含缓存读取的用量统计，不是货币账单。

单次生成 maxTokens 无法限制多工具、多轮 Agent 会话的累计输出。native 路径当前明确不支持全运行 token_limit，因此不应把问题说成“已有全局硬限额失效”。当前缺少的是跨 Agent 步骤、批次和整轮的可执行成本上限。普通样本 0–2 次工具调用只是提示，实际每 attempt 的工具上限为 6。

本轮存在多层重试，但不能简单声称每个样本都被重试 3×2 次。主要浪费来自反复长分析、成组服务故障期间的内部重试，以及在无效批次之后继续推进。

**5. 建议采用的整体方案**

保留现有 Python Host、DSH 插件、网页和账本，不需要新增微服务或第二套流程引擎。收敛为以下责任边界：

`任务与冻结预算 → 路由健康准入 → 逐样本 Agent/工具/所需评审 → 执行有效性检查 → batch 反思 → 冻结候选 → epoch 共同评测 → 选择或保留 → 独立认证`

**第一步，统一错误契约和运行健康控制，优先级 P0。**

跨 DSH、HTTP、Python、账本保留宿主可验证的故障域、错误码、provider 状态、可恢复性、retry-after 和影响范围。503、429、连接超时、结构错误、工具协议异常、输出耗尽分别处理。

健康控制以 provider/model 路由聚合，而不是让每个样本各自等待和重试。建议起始规则为：同一路由连续 3 个可恢复服务故障，或最近至少 10 个请求中服务失败达到 30%，暂停新派发；尊重 Retry-After，冷却后只允许一个半开探测。已在途请求有界排空，成功结果仍保存。上述阈值是待故障注入和小实验验证的初始建议，不是已测最优参数。

准入控制必须接收显式运行健康结果；业务函数返回不等于远端成功。多层重试共享总次数和总时间预算，由请求层承担少量短重试、路由层承担长冷却，Host 重排仍未完成的工作。限制请求数、Agent 步数、工具调用数和墙钟时间；provider token 回执用于审计和预算预警，不虚构不可保证的精确账单硬上限。

**第二步，按实际 sample.plan / sample.critic 协议验证模型路由，优先级 P0。**

现有 canary 只验证 generation.search-plan 和 generation.reflect 的短 fixture，未覆盖真正失败的 sample.critic preset。应增加同 route/preset/schema/tool surface 下的短、长上下文和真实预测工具链检查，明确每个角色的通过范围；一次通过不代表数小时稳定。

对普通文本 DSML，保持拒绝执行。通过脱敏的原始响应形状与 DSH 事件对照，定位解析断点；修正确的 provider 工具协议适配，或使用验证通过的路由并建立新的冻结绑定。一次孤立协议异常可在预算内进行一次新的真实协议检查；重复出现则隔离路由，保留检查点，避免继续消耗整轮。

只要调整了模型、工具契约、预算或算法绑定，就应生成新协议版本/实验谱系。现有已失败 run 保留为诊断记录，不能静默改其身份后宣称原运行继续完成。

**第三步，先恢复有效执行，再允许科学状态推进，优先级 P0。**

为样本、batch、评测臂明确区分：正在执行、等待恢复、执行无效、执行有效但科学不通过、科学通过。attempted 数只决定是否已尝试完，不能直接授予评测资格。

可恢复失败优先补全同一冻结时点和未完成阶段。已接受的 planner 预测与工具证据保留；critic 中断后，在同一契约和可验证绑定下恢复 critic，避免重算整个样本。新实现要保证反馈标签在该阶段有效完成之前不回流；修复提示只能包含运行/格式诊断，不能利用已知标签修到通过。

当路由共同故障或整批无有效预测时，停在运行恢复状态；不能再派发后续 batch、生成“科学保留旧版”决定或进入 holdout。预筛全不通过必须进一步分流：执行不可用先恢复；执行有效但分数不好可以做预算受限探索。轮末首副本无效先恢复或标为不可评估，不再自动执行昂贵的认证副本。保留完整预声明 cohort，不能只挑成功子集来做晋升比较。

**第四步，采用符合 100/10/50 目标的快速实验默认结构，优先级 P1。**

建议将当前多候选并行对照流程与快速实验明确分开，作为不同冻结协议。快速实验默认：

1. 每轮只有一条训练主线，100 个训练时点、10 个 batch；每个时点仍由 Agent 自主分析、选工具和提交预测。
2. 每批开始前冻结策略；10 个时点完成且标签成熟后反思，产生供下一批使用的探索修订。此时只记录“已应用待验证”，不称为已验证提升。
3. 轮末锁定一个候选，建议默认使用最后一个合法训练修订；与本轮开始时的冻结冠军，在相同的 50 个后续时点上各评一次。
4. 只有两臂运行证据完整、达到预声明的探索选择门槛，才更新工作冠军；否则保留旧冠军或报告不可评估。

| 快速实验正常路径 | 次数 |
|---|---:|
| 主线训练 | 100 |
| 轮末候选评测 | 50 |
| 轮初冠军对照 | 50 |
| 每轮样本执行 | **200** |
| 5 轮基础样本执行 | **1000** |

单轮使用 150 个不同的训练/评测时点，对应 200 次 Agent 样本执行。200 不是所有 LLM 请求数：研究、批次反思、所需 critic、工具与修复另列限额。成本预览必须展示这些区别，并允许无候选变化或证据不足时按预声明规则提前结束。

默认固定复用同一组 100 个训练时点进行跨 epoch 的训练回放，每轮使用新的一组 50 个后续比较时点；因此 5 轮至少需要 100+5×50=350 个不同可用起点，独立认证区另计。训练回放不是新增独立证据，训练成绩也不代表样本外泛化。执行计划必须记录复用身份、各轮比较边界和数据容量；对两个真实数据集重新核验目标成熟隔离、日块覆盖及最终独立区，不能仅按350条记录判断足够。

这里“轮末择优”是预先锁定的候选与轮初冠军二选一。不能把不同 batch、不同时间片的分数直接排序成历史最优；若要比较多个历史修订，需要共同评测规则和额外预算，并在揭示轮末标签前确定。

快速协议需要重新冻结选择规则和统计解释，不能复用原双副本认证标记。它只支持预声明小实验下的探索性择优，不证明 Agent 推理稳定性或独立泛化提升。各 epoch 使用新的后续比较时点；一旦结果用于搜索，就属于自适应选择证据。最终认证继续使用隔离的后续数据、时间块统计、分项不退化、重复推理及多次选择校正。

原 4 候选、64 时点预筛、Top 2、新旧双臂和双副本结构保留为显式选择的正式对照模式；该模式也必须经过前述运行健康检查。无需把所有实验都塞入当前固定重流程。

**第五步，压缩单样本 Agent 的重复分析，优先级 P1。**

把批次共享策略、已拟合模型工件和必要因果信息组织成紧凑上下文。样本 Agent 仍自行决定是否用工具，但普通时点优先继承批次策略；新增深度探索需要有明确不确定性理由和剩余预算。模型选型的广泛比较、参数搜索和策略总结集中在批次/轮次反思，避免每个时点重复搜索整套模型。

工具返回只携带当前预测所需数据、质量诊断和来源凭证。相同冻结模型、参数与输入下可复用确定性计算；不同时间点的未来信息和评测标签不得进入缓存上下文。优先降低上下文、工具循环和冗长输出，再校准单次生成额度；直接加大 token 上限会放大耗时，盲目压低则增加截断。

**第六步，统一展示并设置发布门槛，优先级 P1/P2。**

所有预算和限制来自一份冻结执行计划。运行首页优先展示：当前阶段、路由健康、有效/失败/待恢复样本、真实版本晋升、已经花费和剩余阶段预算。分别标明“批次尝试完成”“执行有效”“修订已提议”“修订已验证”；恢复建议依赖错误域，不统一提示重新新建。

补上执行健康遥测：当前真实准入、等待数、路由冷却原因、provider 状态、重试所属层、总尝试次数、已接受阶段与未完成阶段。用来源明确的事件驱动读模型，避免多个页面各自推断业务状态。

**6. 推荐实施与验收顺序**

| 顺序 | 实施范围 | 验收标准 |
|---|---|---|
| A：故障回放 | 503/429/连接、DSML 普通文本、schema、输出耗尽、取消/持久化 | 分类穿过 JS→HTTP→Python 后不丢失；服务故障不变成科学差评；真实工具授权保持有效 |
| B：恢复与停止 | 路由共同故障、整批失败、critic 中断、重启 | 熔断后只保留已在途有界工作；不启动后续 batch/holdout；已接受 planner 不重复计算；恢复只补冻结工作 |
| C：真实链路小实验 | 先做 20–30 个时点的完整 Agent 链路和不同上下文协议检查 | 记录所有失败、恢复、用量、成功预测；确认 DSML 原因已解决，不仅看最终 JSON 是否存在 |
| D：快速协议 1 轮 | 100/10/50、单主线、双臂单副本 | 实际执行量与计划一致；至少发生真实反思；版本更新与晋级计数准确；完整共同评测才能择优 |
| E：连续 5 轮 | 完整新实验，执行过程中模拟短暂服务中断 | 没有孤立 running、无效阶段仍推进、预算超限继续派发或重复接受结果；每轮结论与账本一致 |
| F：正式认证/交付 | 固定算法与路由，独立时序数据和正式统计协议 | 有独立有效证据后才报告稳定提升；未改善可以如实完成，不能以出现新版本代替效果证明 |

建议第一阶段把成功样本 planner 中位耗时降低至少 40%、每有效样本用量降低至少 50% 作为对照目标，基于相同诊断时点、相同角色和目标验证；这些是待测目标，不是本次已达到的性能承诺。比“跑满 5 轮”更先决的发布条件，是服务故障不再污染评测、预算能够停止新增调用、检查点可验证恢复。
