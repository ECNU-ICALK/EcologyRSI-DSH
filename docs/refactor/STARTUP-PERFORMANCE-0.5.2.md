# 0.5.2：启动与历史加载优化

本版包含 0.5.1 的整体审查修复，并进一步处理服务启动、缓存失效后页面等待历史数据的问题。

## 实测瓶颈

现有活动运行期间，热态网页首次可用约 0.98 秒。但冷缓存下，原来的五条运行列表会恢复完整状态，连带验证科学比较并编码完整检查点；带性能探针的单次读取达到 15.82 秒。问题不是列表条目数量本身，而是每条列表记录触发了与其展示需求无关的历史计算。

独立测量使用已完成历史运行的 SQLite 快照；每次创建独立数据库路径，不复用读取缓存。排除数据库复制和服务初始化、不开性能探针、各执行三次：

| 五条运行列表 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 读取耗时中位数 | 5,697 ms | 4.76 ms |
| JSON 行数据大小 | 54,039 字节 | 2,239 字节 |

这些数值只衡量运行选择列表，不代表整页或模型运行速度获得同等倍数的提升。完整科学证据仍需要在选中运行后恢复和验证。

## 修改

1. 列表直接利用事件表已有索引读取运行身份、生命周期、轮次、候选数量、时间和自动推进标记；单条 SQL 保持读取快照一致，不新增并行状态机或持久化业务表。
2. 精简列表合同为 `browser-run-summary/2`，保留归档过滤、稳定分页、取消空运行识别、任务分区和评测分区检查。科学结果、模型预检证据、配置详情留在选中运行的页面，不由列表推断。
3. 首屏配置与所选运行概况解耦。目录和列表就绪后页面可以操作，历史详情在后台读取，并在运行栏显示加载状态；失败只影响该区域。
4. 后台概况响应受请求顺序约束。切换运行或创建新运行后，旧响应不能夺回当前选择。
5. 数据容量核验是只读操作，移出全局写操作锁，避免等待其他运行的修改，也避免加载数据时占用暂停等控制所需的锁。

## 验证与使用边界

新增回归检查冷列表不调用完整状态回放或事件流解码、隐藏分区拒绝、后台加载不阻塞、失败隔离、迟到响应，以及列表不虚构科学结果。

真实 Chrome 的独立冷启动中，配置控件约 0.37 秒就绪，历史概况约 9.43 秒就绪。概况未返回时可以正常切换参数页，期间未记录到浏览器长任务。该次测量同时运行其他本地负载，不作为无负载延迟承诺。

本次验收使用独立后端和历史快照，不重复执行生产中的自进化。生产运行 `run:a39ff5dc-af48-43ad-8c9d-5484d050a9d2` 仍在 0.5.0 进程中执行；本次保留该进程，后端优化在随后重启到 0.5.2 时生效。前端静态文件已更新。页面版本号不表示已有执行进程已经升级。

本地审计目录：`.runtime/startup-performance-20260907/`。性能原始值见 `index-benchmark.json`，全量回归见 `full-tests.log`，真实浏览器验收见 `browser-acceptance.json`。最终验证结果记录在该目录的 `verification-summary.json`。

当前构建来自包含既有未提交修改的工作区，交付包保留真实的 `dirty=true` 构建信息；它是本地候选构建，不冒充已提交的正式发布。
